# 4. 验证策略

[English](04-verification-strategy.md) | [繁體中文](04-verification-strategy.zh-TW.md) | **简体中文**

每一层都回答一个前一层回答不了的问题。

| 层级 | 回答什么 | 在哪里 |
| --- | --- | --- |
| 回归测试 | 这个缺陷修复后，会不会再犯？ | `tests/`：CI 在 Python 3.11 和 3.12 上运行；其中需要 Docling 的 5 个在那里会跳过，改由另一个安装 Docling 的任务运行 |
| 发行运行时测试 | *打包后*的启动器，在只有锁定软件包的情况下，行为正确吗？ | `tests/test_release_packaging.py`：另外 9 个，在 CI 的 Linux 上运行，并在 Mac 上手动运行 |
| 真实硬件 | 能在它要发行的平台上构建、签名、运行吗？ | 负责人的 Apple Silicon Mac |
| 干净的机器 | 它带齐了所需的一切吗？ | macOS 虚拟机，[SOP](../../docs-release/macos-vm-verification.md) |
| UAT | 在每种情况下，用户实际看到的是什么？ | [`verification/2026-10-13-uat/`](../../verification/2026-10-13-uat/REPORT.md) |
| CI 检查 | 依赖安全吗？许可没问题吗？没有泄露密钥吗？ | 两个 workflow，在推送到 `main` 和对 `main` 提 PR 时运行；只改文档时不运行 |

## 每个回归测试都对照 bug 验证过

修复之后才写的测试，可能因为错误的理由而通过——它测的是新的代码路径，却从没真正触发旧的失败。
所以每个测试都反过来验证过一次：**把缺陷放回去，确认测试会失败。**许可声明收集器、HTML 实体修复、
下载文件命名、空结果防护和拒绝提示，都是这样验证之后才合并的。

## 打包后应用的测试在 CI 中运行，对照锁定版本

发行运行时测试会在一个只有锁定软件包的隔离 Python 环境中启动真正的启动器，再通过 HTTP 与它通信。
环境不存在时，每个测试都会自行跳过。有一段时间 CI 没有创建这个环境，所以在 `main` 上，CI 报告的是 **180 个通过、9 个跳过**。

现在另有一个 CI 任务会创建两个环境——`text` 和 `pdf`——并在其中运行这九个测试，不安装任何测试依赖。
只要有任何测试被跳过，这个任务就会失败，所以缺少环境会变红，而不是悄悄通过。

它检查的是锁定的*版本*，不是实际发行的那些文件。lock 文件里的哈希值对应的是 macOS arm64 的 wheel，
所以在 Linux 运行器上，环境是从不带哈希值的需求文件创建的：版本相同，但是 Linux 版。
那些 macOS wheel 本身是否正常，仍然要在负责人的 Mac 上回答——在那里，测试对照的是按哈希锁定文件创建的环境。

这份案例研究一开始写的是测试“0 个跳过”。这在有那些环境的机器上是对的，在 CI 中却不是——
和[第 3 章第 3 项](03-silent-failures.zh-CN.md#3-十六个被跳过的测试被算作通过)是同一个错误，
而且是在写这份记录时又犯了一次。它是靠读 CI 日志、而不是凭记忆中的本地结果才发现的，并由上面那个 CI 任务补上了缺口。

## 一个让缺陷溜过去的验证缺口

在第一次真正的 Mac 构建之前，`pdf` 配置先在 Linux 上用 PyInstaller 试构建过。
那次试构建发现了一个真正的问题：冻结后的应用第一次转换 PDF 就失败了，因为 `latex2mathml` 里的一个数据文件没有被打包进去。

但那次试构建是直接运行 PyInstaller，从没运行过收集许可声明的步骤，
所以那 21 份被悄悄漏掉的声明（[第 3 章第 7 项](03-silent-failures.zh-CN.md#7-被悄悄漏掉的许可声明)）
一直没人看到，直到负责人在 Mac 上构建。修复方式是一个工具，无需构建就能在任何地方检查每个锁定软件包的许可声明——
`scripts/packaging/audit_notices.py`——这个问题从此不再需要目标机器才能回答。

## UAT

七份合成文档，每份都针对这个项目修复过的一个缺陷，跑过四种输出和两个发行配置。
接着是用户可能出错的十四种方式——不支持的格式、超出上限的文件、六个文件、一个都没选、Big5 编码的文本文件、
空文件、跨站请求——在两个配置上各跑一次，并**逐字记录每一种的提示**。

它找到了四个缺陷，包括空文件被当作成功（[第 9 项](03-silent-failures.zh-CN.md#9-空的转换结果被当作成功返回)），
以及在中文页面上用英文回答的提示。

它也产生了一次误报，这同样值得记录。有一份输出写着 `R&D;`，多了一个分号。在把它当作 bug 之前，
先用 `pypdf`——与这个项目无关的工具——读取了那个 PDF：分号本来就在 PDF 里，是生成样例的工具把单独的 `&` 弄坏了。
转换器忠实地还原了内容。**在排除输入本身的问题之前，不报告缺陷。**

## 只提交合成文档

所有提交进来的测试输入和验证样例，都是由仓库里的脚本生成的。`.gitignore` 排除了 `*.pdf`，
所以真实文档不会被意外加进来。在把仓库公开之前，检查了当前的文件**以及完整的 git 历史**：从来没有任何文档被提交过。

## 没验证的，明确说出来

| 没验证 | 原因 |
| --- | --- |
| 在第二台 Mac 上安装 | 只有一台 Mac。虚拟机流程能覆盖干净机器会暴露的问题，但覆盖不了不同代的芯片或不同的 macOS 版本 |
| Developer ID 签名、公证 | 没做；每个构建都标记为 `distribution_ready: false` |
| Docling 的模型流程 | 智能体的环境连不上模型的下载主机。两个发行配置都没用到它 |
| OCR | 没有附带，所以也不宣称 |
| Windows | 没有安装包，没有测试 |

README 的状态表对应用也写了同样的事。一句“已验证”，结果原来是“在我试过的那一条路径上验证过”——
第 3 章的第 3、4 项就是这样发生的。
