# 5. 许可与合规

[English](05-licensing-and-compliance.md) | [繁體中文](05-licensing-and-compliance.zh-TW.md) | **简体中文**

项目自己的代码采用自定义许可证；它的应用里却附带了大约六十个别人的软件包。这两件事必须同时成立。
证据在 [`docs/LICENSE_AUDIT.md`](../LICENSE_AUDIT.md) 和 [`THIRD_PARTY_NOTICES.md`](../../THIRD_PARTY_NOTICES.md) 中；
这一章说明是怎么走到那一步的。

> 这是核查了什么的记录，不是法律意见。审计文档对自己也是这么说的。

## 按许可证决定附带什么

许可工作在任何代码被打包之前就开始了：应用里放什么，有一部分是看它的许可证允许应用做什么来决定的。

| 候选 | 许可证 | 结果 |
| --- | --- | --- |
| PyMuPDF / MuPDF | AGPL-3.0，或 Artifex 商业许可 | **不附带。** AGPL 的效力会扩展到整个应用；商业许可则要花一笔项目没必要花的钱 |
| `pypdfium2` + PDFium | BSD-3-Clause 或 Apache-2.0；PDFium 的组件均为宽松许可 | **附带**于 `pdf` 配置，作为 PDF 读取器 |
| Docling，免模型流程 | MIT | **附带**于 `pdf` 配置。它的模型流程没有附带，它的模型也从未审查过 |
| Marker | 代码 Apache-2.0；模型权重另有条款，带有商业限制 | 可选引擎，由用户自行安装，从不打包 |
| MinerU 4.x | Apache-2.0 加附加条款：月活跃用户超过 1 亿或月收入超过 2,000 万美元需另行获取许可，在线服务必须注明使用了 MinerU | 可选引擎，从不打包。较早的 `magic-pdf` 包是 AGPL-3.0 |

“可选”本身没有任何法律效力。用户自行安装的引擎仍适用它自己的条款；
审计文档把这些条款记录下来，让安装的人看得到自己同意了什么。

## `pdf` 版应用实际包含什么

| | |
| --- | --- |
| 软件包 | 60 个，以哈希值锁定 |
| GPL 或 AGPL 的运行时代码 | 无 |
| 弱 copyleft | `certifi` 和 `tqdm`（MPL-2.0），未经修改直接附带——MPL 的义务只及于修改过的文件 |
| PyInstaller | GPL-2.0-or-later，**附带它的 Bootloader 例外条款**，允许把 bootloader 放进应用发行，而 GPL 不会扩展到应用本身 |
| PDFium | 一个二进制文件，包含 15 份组件许可证：FreeType、libjpeg-turbo、ICU、libpng、zlib、OpenJPEG、Little CMS、Abseil 等 |
| 构建好的应用中的许可声明 | 124 个文件，涵盖 60 个软件包，位于 `Contents/Resources/legal/` |

## 读许可证原文，不只看标签

许可证标签——“BSD”、“MIT”——说的是适用哪一类条款，没说这些条款要求你做什么。
把 PDFium 的 15 份组件许可证逐一读过，发现其中两份**要求**在只发行编译后程序时，在发行文档中加上一句话：

- *This software is based in part on the work of the FreeType Team.*
- *This software is based in part on the work of the Independent JPEG Group.*

两句现在都写在 `THIRD_PARTY_NOTICES.md` 中，随每个安装包一起发行。第一轮只找到 FreeType。
IJG 的要求在一个单独的文件 `libjpeg_turbo.ijg` 里，是把每一份附带的许可证文件完整读完才找到的。
其中有四份许可证还禁止用作者的名义做宣传，所以这些声明写成文档说明，而不是背书。

## 许可声明丢失的时候

构建是按文件名收集许可证文件的——`LICENSE`、`COPYING`、`NOTICE`。按照现行标准
（[PEP 639](https://peps.python.org/pep-0639/)）打包的软件包，会把许可证文件放在 `licenses/` 文件夹里，
文件名由上游决定，例如 `freetype.txt`。这类文件共 21 个，全被悄无声息地漏掉了，包括 `pypdfium2` 的 18 个。

问题是在负责人的 Mac 上暴露的：构建停了下来，因为 `latex2mathml` 完全没有许可声明。
追查原因后发现，3.81.0 和 3.81.1 两个版本都没有附带许可证文件，而收集器另外还有一个更隐蔽的漏洞。
[#5](https://github.com/Jake627520/documnet_converter/pull/5) 的修复：

- 除了按文件名匹配，也匹配那个标准位置；
- 把 `latex2mathml` 锁定在 3.80.0，这个版本附带了许可证文件；
- 新增 `scripts/packaging/audit_notices.py`，按哈希值下载每个锁定的 wheel，用构建本身的规则检查，
  完全不用安装——所以这个问题在构建之前、在任何机器上都能回答。

构建大声地失败，是好的结果。那 21 份被漏掉的声明，可是连一个错误都没有产生。

## 写给另一个版本的文档

法律文档是为第一版应用写的，那一版不含任何文档引擎。后来 `pdf` 配置加入了 Docling 和 PDFium——
文档却仍然写着 Docling 被排除在外。没有任何东西会拿文字描述去对照依赖清单。

这是在负责人要求公开前再确认一次许可时发现的，并在 [#6](https://github.com/Jake627520/documnet_converter/pull/6) 中修复。
从中得出的规则：**发行内容的变更，就是法律文档的变更**，放在同一个 PR 里。

## 公开不等于开源

仓库是公开的；许可证没有改变。自定义的 [`LICENSE`](../../LICENSE) 允许个人使用和公司内部使用，
包括内部商业用途，并限制原始代码的转售和再分发。这不是开源许可证——
[开源定义（Open Source Definition）](https://opensource.org/osd)要求再分发的自由。

公开只多了一件事：GitHub 的服务条款让任何人都能查看这个仓库，并在 GitHub 上 fork。
README 的 fork 说明写了这样做允许什么、不允许什么。第三方条款无论仓库公开还是私有都一样。

## 重建组件以避开它的许可证

在评估各种方案时出现过一个问题：能不能用逆向工程工具，把一个许可证有限制的组件重建成项目自己的东西？

没办法用这种方式让条款消失。从另一个程序反编译或反汇编出来再重建的代码，仍然是由它衍生而来的，
而且很多许可证直接禁止逆向工程。行得通的路，是这个项目已经走的或保留的这几条：

- **选择宽松许可的替代品**——用 PDFium，而不是 MuPDF；
- **购买商业许可**，如果对方提供的话；
- **净室实现（clean-room）**——由没有研究过原始程序的人，依据公开规格编写。
  这是一套有自己记录的法律流程，不是编程智能体能替自己担保的事。

## AI 辅助创作

这个项目大部分代码由 AI 编程智能体编写。
[美国版权局 2025 年 1 月的报告](https://www.copyright.gov/ai/)认为，版权保护及于人的创作贡献——
选择、编排、修改——但不及于由 AI 系统决定的表达；仅仅给出提示不构成创作。
这个项目有多少可受保护的部分，尚未评估。

这会影响项目自己的许可证能在多大程度上约束它自己的代码。它完全不改变第三方条款——那些条款无论如何都约束这个项目。
审计文档把它记录为一个未解决的问题，它本来就是。
