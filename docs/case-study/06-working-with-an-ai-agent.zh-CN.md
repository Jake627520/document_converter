# 6. 与 AI 编程智能体协作

[English](06-working-with-an-ai-agent.md) | [繁體中文](06-working-with-an-ai-agent.zh-TW.md) | **简体中文**

这个仓库里的代码、测试和文档，都是由 AI 编程智能体（Claude Code）编写的。负责人没有写代码。
这一章讲的是这样的分工如何运作、在哪里出错，以及是什么让那些错误没有发行出去。

## 谁做了什么

| 智能体 | 负责人 |
| --- | --- |
| 编写代码、测试、构建脚本和文档 | 决定做什么、不做什么 |
| 诊断失败原因并提出修复方案 | 在方案之间做选择 |
| 提 PR，一个 PR 只处理一件事 | 决定每个 PR 何时合并，或要求修改 |
| 运行测试、CI 检查和 UAT | 在真实的 Mac 上构建应用，并用在真实文档上 |
| 研究许可证、上游工具和平台规则 | 决定许可证、是否公开，以及为什么付费 |

## 由负责人做的决定

以下每一项都有合理的替代方案。智能体把方案摆出来；负责人做选择。

- **不用 PyTorch**，所以没有版面模型、没有 OCR——应用小得多、在任何 Mac 上都能运行，代价是扫描文档
  （[第 1 章](01-problem-and-scope.zh-CN.md)）。
- **Mac 应用支持 PDF**，做成第二个发行配置，而不是让应用只处理文本文件。
- **一次修复三个 CI 失败**，在第一个 PR 里全部处理，而不是只修提 PR 时要修的那一个。
- **放弃 Python 3.10。** 处理这件事的 PR 后来关闭了，因为它的变更已经随另一个 PR 进了 `main`。
- **暂不申请 Apple Developer 账号**（每年 99 美元）：改用虚拟机验证，并明确说明应用没有签名。
- **把仓库公开**，保留现有许可证，作为免费工具，在先研究过已有哪些类似工具之后——
  并亲自按下那个开关，因为公开之后无法撤回。
- **把案例研究放在这里**，放在公开的仓库中，而不是另开一个展示用的仓库。
- **修正“MiB”的写法**：听完为什么这样写之后，选择补上大家熟悉的 MB，而不是只保留更精确但更陌生的单位。

## 找出缺陷的那些问题

负责人的问题，往往就是暴露问题的关键——不是因为这些问题很技术，而是因为它们问的是用户会看到什么。

| 问题或行动 | 找到了什么 |
| --- | --- |
| 在负责人的 Mac 上构建应用 | 21 份许可声明被悄悄漏掉（[第 3 章第 7 项](03-silent-failures.zh-CN.md#7-被悄悄漏掉的许可声明)） |
| 检查负责人转换过的一个文件 | `&` 变成了 `&amp;`——Markdown 输出把 HTML 实体重复转义了 |
| README 列出的输出格式，网页上却没有？ | `.json` 和 `.txt` 只有命令行才有 |
| 能再确认一次许可吗？ | 法律文档描述的是一个不支持 PDF 的项目（[第 8 项](03-silent-failures.zh-CN.md#8-描述错了产品的法律文档)） |
| 用户上传没有文字的图片，会得到什么？ | 一次成功的下载，内容是空文件（[第 9 项](03-silent-failures.zh-CN.md#9-空的转换结果被当作成功返回)） |
| 如果上传了不支持的格式呢？ | 中文页面上的英文错误提示，而且什么都没说明 |
| 为什么是“MiB”而不是“MB”？ | 页面除以 1,048,576，却把结果标为 MB（[第 10 项](03-silent-failures.zh-CN.md#10-同一个文件两种大小)） |

这些都不需要负责人懂代码如何运作，每一个需要的都是有人从产品外部去看它。

## 智能体自己犯的错

这些是智能体的错，而且每一个都在发行前被发现——有些是智能体自己发现的，更多是负责人发现的，
全都是靠拿真实的东西来对照。

| 错误 | 如何发现 |
| --- | --- |
| 给负责人的构建路径，文件夹名称少了 `-pdf-` | 负责人的终端：找不到这个目录 |
| 建议用“右键 › 打开”绕过 Gatekeeper——Apple 在 macOS 15 已移除这种方式 | 准备虚拟机流程时，核实了 Gatekeeper 当前的行为 |
| 提议用 `--skip-editable` 修复依赖审计，却没有实测；项目并不是以 editable 方式安装的，所以它根本不会起作用 | 在编写修复之前，先复现 CI 的环境 |
| 加入 `pdf` 配置，却没有更新法律文档 | 负责人要求再确认一次许可 |
| 找到了 FreeType 的声明要求，却漏了 IJG 的 | 把每一份附带的许可证文件完整读完 |
| 说某个下载文件命名行为不是有意的；其实测试名称就表明那是一个安全上的选择 | 在修改之前先读了那个测试 |
| 把一个无关的变更放进了一个提交，而提交信息没有描述它 | 检查提交时发现，拆成了两个 |
| 在这份案例研究中写测试“0 个跳过” | 读 CI 日志（[第 4 章](04-verification-strategy.zh-CN.md#打包后应用的测试在-ci-中运行对照锁定版本)） |

模式和第 3 章一样：凭记忆、或凭单一环境就下的结论，而不是拿东西本身来对照。

## 是什么让错误没有发行出去

- **每个变更都经过 PR**，一个 PR 只处理一件事，合并前 CI 必须全绿。智能体只在负责人说要合并时才合并。
- **每个修复都附带一个“没有这个修复就会失败”的测试**
  （[第 4 章](04-verification-strategy.zh-CN.md#每个回归测试都对照-bug-验证过)）。
- **真实硬件、真实文档。** 负责人的 Mac 构建和负责人自己的文件，找到了智能体环境里再多测试都找不到的问题。
- **个人数据不进仓库。** 负责人的真实文档只用来检查输出，从不提交；每个提交进来的样例都是合成的。
- **无法撤回的步骤留给负责人**——公开仓库、购买证书、决定合并。
- **“没验证”是一个正当的答案。** 智能体的环境连不上某些主机，也没有 Mac。没核查过的地方，文档就直说没查，而不是暗示查过了。

## 给类似项目的启示

一个智能体可以编写并测试这种规模的产品。它无法提供的，是外部视角：一个真正在用这个东西的人，
在自己的机器上、用自己的文档，并问它应该做什么。第 3 章的十个缺陷，大多数就是在这个交界处找到的。
