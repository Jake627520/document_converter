# 4. Verification strategy

**English** | [繁體中文](04-verification-strategy.zh-TW.md) | [简体中文](04-verification-strategy.zh-CN.md)

Each layer answers a question the one before it cannot.

| Layer | Answers | Where |
| --- | --- | --- |
| Regression tests | Does this exact defect stay fixed? | `tests/`: 226, run in CI on Python 3.11 and 3.12; the 5 that need Docling skip there and run in a job that installs it |
| Release runtime tests | Does the *packaged* launcher behave, with only the pinned packages present? | `tests/test_release_packaging.py`: 9 more, run in CI on Linux and by hand on the Mac |
| Real hardware | Does it build, sign and run on the platform it ships for? | The owner's Apple Silicon Mac |
| Clean machine | Does it carry everything it needs? | A macOS virtual machine, [SOP](../../docs-release/macos-vm-verification.md) |
| UAT | What does a user actually see, in every case? | [`verification/2026-10-13-uat/`](../../verification/2026-10-13-uat/REPORT.md) |
| CI checks | Are the dependencies safe, licensed, and free of secrets? | Two workflows on pushes to `main` and pull requests into it, except changes to documentation only |

## Every regression test is checked against the bug

A test written after a fix can pass for the wrong reason — testing the new code
path without ever exercising the old failure. So each one was checked the other
way: **put the defect back, and confirm the test fails.** The notice collector,
the entity fix, download naming, the empty-result guard and the rejection
messages were all checked like this before being merged.

## The packaged app's tests run in CI, against pinned versions

The release runtime tests start the real launcher in an isolated Python
environment holding only the pinned packages, then talk to it over HTTP. Each
one skips itself when that environment is absent. For a while CI did not build
it, so on `main` CI reported **180 passed, 9 skipped**.

A separate CI job now builds both environments — `text` and `pdf` — and runs the
nine tests from them, with no test dependency installed. The job fails if any
test skips, so a missing environment turns red instead of quietly passing.

It checks the pinned *versions*, not the exact artifacts that ship. The lock
files' hashes name macOS arm64 wheels, so on the Linux runner the environments
come from the unhashed requirement files: the same versions, as Linux builds.
Whether those exact macOS wheels behave is still answered on the owner's Mac,
where the tests run against environments built from the hashed locks.

This case study first said the suite ran with "0 skipped". That was true on the
machine where the environments existed, and not in CI — the same mistake as
[Chapter 3, item 3](03-silent-failures.md#3-sixteen-tests-skipped-counted-as-passing),
made again while writing it up. It was caught by reading the CI log rather than
remembering the local run, and closed by the CI job above.

## A verification gap that let a defect through

Before the first real Mac build, the `pdf` profile was trial-built on Linux with
PyInstaller. That trial caught a real problem: the frozen app failed its first
PDF conversion because a data file inside `latex2mathml` was not being bundled.

But the trial ran PyInstaller directly. It never ran the notice-collection step,
so the 21 silently dropped notices ([Chapter 3, item 7](03-silent-failures.md#7-license-notices-silently-dropped))
went unseen until the owner's build on the Mac. The fix was a tool that checks
every pinned package's notices from anywhere, without building —
`scripts/packaging/audit_notices.py` — so that question no longer needs the target
machine to answer.

## The UAT

Seven synthetic documents, each aimed at a defect this project had fixed, through
four outputs and both release profiles. Then fourteen ways a user can get it
wrong — an unsupported format, a file over the limit, six files, none, a Big5
text file, an empty file, a cross-site request — in both profiles, with **the
exact message recorded for each**.

It found four defects, including the empty-file success
([item 9](03-silent-failures.md#9-an-empty-conversion-returned-as-a-success)) and
messages that answered in English on a Chinese page.

It also produced a false alarm, and that is worth recording too. One output read
`R&D;` with a stray semicolon. Before calling it a bug, the PDF was read with
`pypdf`, independently of this project: the semicolon was in the PDF itself —
the tool that generated the sample had mangled a bare `&`. The converter had been
faithful. **A defect is not reported until the input has been ruled out.**

## Only synthetic documents are committed

Every committed test input and verification sample is generated by a script in
the repository. `.gitignore` excludes `*.pdf`, so a real document cannot be added
by accident. Before the repository was made public, the tree **and its full git
history** were checked: no document has ever been committed.

## What is not verified, said plainly

| Not verified | Why |
| --- | --- |
| Installing on a second Mac | One Mac was available. The VM procedure covers what a clean machine reveals, but not different chip generations or macOS versions |
| Developer ID signing, notarization | Not done; every build is marked `distribution_ready: false` |
| Docling's model-based pipeline | The agent's environment could not reach the model host. Neither release profile uses it |
| OCR | Not shipped, so not claimed |
| Windows | No installer, no testing |

The README's status table says the same for the app. A claim of "verified" that turns out to
mean "verified on the one path I tried" is how items 3 and 4 in Chapter 3 happened.
