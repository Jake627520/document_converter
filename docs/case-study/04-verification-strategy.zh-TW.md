## 每個回歸測試都對照 bug 驗過

修好之後才寫的測試，可能因為錯誤的理由而通過——它測的是新的程式路徑，卻從沒真正觸發舊的失敗。
所以每個測試都反過來驗過一次：**把缺陷放回去，確認測試會失敗。**授權聲明收集器、HTML 實體修正、
下載檔命名、空結果防護和拒絕訊息，都是這樣驗過之後才合併的。

## 打包後 App 的測試在 CI 裡跑，對照鎖定版本

發行執行階段測試會在一個只有鎖定套件的隔離 Python 環境裡啟動真正的啟動器，再透過 HTTP 和它溝通。
環境不存在時，每個測試都會自己跳過。有一段時間 CI 沒有建立這個環境，所以在 `main` 上，CI 回報的是 **180 個通過、9 個跳過**。

現在另有一個 CI 工作會建立兩個環境——`text` 和 `pdf`——並在其中執行這九個測試，不安裝任何測試用套件。
只要有任何測試被跳過，這個工作就會失敗，所以少了環境會變紅，而不是悄悄通過。

它檢查的是鎖定的*版本*，不是實際出貨的那些檔案。lock 檔裡的雜湊值指的是 macOS arm64 的 wheel，
所以在 Linux 執行器上，環境是從沒有雜湊值的需求檔建立的：版本相同，但是 Linux 版。
那些 macOS wheel 本身是否正常，仍然要在負責人的 Mac 上回答——在那裡，測試對照的是依雜湊鎖定檔建立的環境。

這份案例研究一開始寫的是測試「0 個跳過」。這在有那些環境的機器上是對的，在 CI 裡不是——
和[第 3 章第 3 項](03-silent-failures.zh-TW.md#3-十六個被跳過的測試被算成通過)是同一個錯，
而且是在寫這份紀錄時又犯了一次。它是靠讀 CI 紀錄、而不是憑記憶中的本機結果才抓到的，並由上面那個 CI 工作補上了缺口。

## 一個讓缺陷溜過去的驗證缺口

在第一次真正的 Mac 建置之前，`pdf` 設定檔先在 Linux 上用 PyInstaller 試建置過。
那次試建置抓到一個真正的問題：凍結後的 App 第一次轉換 PDF 就失敗了，因為 `latex2mathml` 裡的一個資料檔沒被打包進去。

但那次試建置是直接跑 PyInstaller，從沒跑過收集授權聲明的步驟，
所以那 21 份被默默漏掉的聲明（[第 3 章第 7 項](03-silent-failures.zh-TW.md#7-被默默漏掉的授權聲明)）
一直沒人看到，直到負責人在 Mac 上建置。修正方式是一個工具，不用建置就能在任何地方檢查每個鎖定套件的授權聲明——
`scripts/packaging/audit_notices.py`——這個問題從此不再需要目標機器才能回答。

## UAT

七份合成文件，每份都針對這個專案修過的一個缺陷，跑過四種輸出和兩個發行設定檔。
接著是使用者可能出錯的十四種方式——不支援的格式、超過上限的檔案、六個檔案、一個都沒選、Big5 編碼的文字檔、
空檔案、跨站請求——在兩個設定檔上各跑一次，並**逐字記錄每一種的訊息**。

它找到了四個缺陷，包括空檔案被當成成功（[第 9 項](03-silent-failures.zh-TW.md#9-空的轉換結果被當成成功回傳)），
以及在中文頁面上用英文回答的訊息。

它也產生了一次誤報，這同樣值得記下來。有一份輸出寫著 `R&D;`，多了一個分號。在把它當成 bug 之前，
先用 `pypdf`——和這個專案無關的工具——讀了那個 PDF：分號本來就在 PDF 裡，是產生範例的工具把單獨的 `&` 弄壞了。
轉換器忠實地還原了內容。**在排除輸入本身的問題之前，不回報缺陷。**

## 只提交合成文件

所有提交進來的測試輸入和驗證範例，都是由 repo 裡的腳本產生的。`.gitignore` 排除了 `*.pdf`，
所以真實文件不會被不小心加進來。在把 repo 公開之前，檢查了目前的檔案**以及完整的 git 歷史**：從來沒有任何文件被提交過。

## 沒驗證的，明白說出來

| 沒驗證 | 原因 |
| --- | --- |
| 在第二台 Mac 上安裝 | 只有一台 Mac。虛擬機程序能涵蓋乾淨機器會暴露的問題，但涵蓋不了不同世代的晶片或不同的 macOS 版本 |
| Developer ID 簽章、公證 | 沒做；每個建置都標記為 `distribution_ready: false` |
| Docling 的模型流程 | 代理的環境連不到模型的下載主機。兩個發行設定檔都沒用到它 |
| OCR | 沒有隨附，所以也不宣稱 |
| Windows | 沒有安裝檔，沒有測試 |

README 的狀態表對 App 也寫了同樣的事。一句「已驗證」，結果原來是「在我試過的那一條路徑上驗證過」——
第 3 章的第 3、4 項就是這樣發生的。
