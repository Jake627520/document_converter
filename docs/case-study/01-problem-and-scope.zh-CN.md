# 1. 问题与范围

[English](01-problem-and-scope.md) | [繁體中文](01-problem-and-scope.zh-TW.md) | **简体中文**

## 问题

处理规格书、内部备忘录和评审文档的人，常常想把它们转换为 Markdown 或纯文本——
放进知识库、wiki，或者交给 AI 助手。这些文档往往是机密的。把它们上传到在线转换网站，
恰恰是最不该做的事。

所以需求说起来简单，做起来容易出错：**在用户自己的电脑上转换，文档绝不发送到任何地方。**

## 为谁而做

| 用户 | 需要 | 因此排除了什么 |
| --- | --- | --- |
| 手上有机密文档的人 | 什么都不离开这台电脑 | 任何云端 API、任何遥测、任何未事先说明就在运行时下载的模型 |
| 不懂技术的同事 | 双击就能用 | “请先安装 Python 3.12，然后……” |
| 开发者 | 从源代码运行、用脚本调用 | 没有命令行的封闭可执行文件 |

于是有了一个核心、三种入口：命令行、只在 `127.0.0.1` 上提供的浏览器工作台，以及打包好的 macOS 应用。

## 为什么不直接用 MarkItDown？

Microsoft 的 [MarkItDown](https://github.com/microsoft/markitdown) 免费、采用 MIT 许可证，
使用非常广泛。单论转换质量，没有赢过它的可能。

但它自己的贡献指南把**桌面应用和 Web 应用列为范围之外**。它是一个库加一个命令行工具。
它留下的空白，正是这个项目瞄准的地方：一个从没打开过终端的人也能用的东西，
而且它对自己说的每一句话都经过核实。

这里的引擎选了 Docling，原因很明确：它有一个 `NativePdfPipeline`，
可以读出 PDF 本来就包含的文字，**完全不加载任何 AI 模型**。下一个决定因此才得以成立。

## 定义了发行版应用的决定：不用 PyTorch

Docling 默认的 PDF 流程会运行版面与表格模型。这些模型需要 PyTorch——安装起来好几个 GB——
而且第一次运行时会下载模型权重。

对一个用于机密文档、双击即开的应用来说，两者都不对：应用会变得非常庞大，
而“首次使用时下载权重”是一次用户没有要求的网络连接。所以负责人的决定是
**完全不用 PyTorch**，基于无需模型的读取器构建。代价是真实存在的，并且在每个相关的地方都写明了：
不重建标题层级、不输出 Markdown 表格、没有 OCR。

## 两种发行配置，各有明确边界

不是一个什么功能都有的应用，而是两种经过审查的配置：

| 配置 | 接受 | 包含 | 存在的理由 |
| --- | --- | --- | --- |
| `text` | `.md` `.markdown` `.txt` | **完全不含文档引擎** | 最小但有用的版本——代码最少，需要负责的许可证也最少 |
| `pdf` | 以上全部，加上有文字层的 PDF | Docling 的免模型读取器和 PDFium | 大家手上实际有的就是 PDF |

配置不是用户可以切换的选项，而是在应用构建时强制执行：构建时拒绝冻结任何列在该配置禁用清单上的模块，
冻结后的应用启动时也会报告没有加载其中任何一个。[第 2 章](02-architecture.zh-CN.md)说明如何做到。

## 有意不做的事

| 不做 | 原因 |
| --- | --- |
| 扫描 PDF 的 **OCR** | 每一种 OCR 方案，不是要下载模型，就是许可证附带条件。扫描件会被报告为没有文字层——绝不靠猜 |
| 应用支持 Office 文档和图片 | 它们需要模型流程，而这个应用的范围正是要避开它 |
| **Apple 公证（notarization）** | 需要付费的 Apple Developer 账号（每年 99 美元）。在应用拥有负责人圈子以外的用户之前，这笔费用不划算；[`docs-release/macos-vm-verification.md`](../../docs-release/macos-vm-verification.md) 说明不靠它也能在干净的机器上测试 |
| Windows | 没有安装包、没有测试——文档也如实这样写，不让人误以为有 |

每一项排除，都写在用户会去找那个功能的地方。写进文档的功能缺失是一个决定；
没写进文档的，就是一份迟早会来的问题反馈。
