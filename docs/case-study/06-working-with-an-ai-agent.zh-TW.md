# 6. 與 AI 程式代理協作

[English](06-working-with-an-ai-agent.md) | **繁體中文** | [简体中文](06-working-with-an-ai-agent.zh-CN.md)

這個 repo 裡的程式碼、測試和文件，都是由 AI 程式代理（Claude Code）撰寫的。負責人沒有寫程式。
這一章談的是這樣的分工怎麼運作、在哪裡出錯，以及是什麼讓那些錯誤沒有出貨。

## 誰做了什麼

| 代理 | 負責人 |
| --- | --- |
| 撰寫程式碼、測試、建置腳本和文件 | 決定要做什麼、不做什麼 |
| 診斷失敗原因並提出修正方案 | 在選項之間做選擇 |
| 開 PR，一個 PR 只處理一件事 | 決定每個 PR 何時合併，或要求修改 |
| 執行測試、CI 檢查和 UAT | 在真的 Mac 上建置 App，並用在真實文件上 |
| 研究授權、上游工具和平台規則 | 決定授權、公開與否，以及要為什麼付錢 |

## 由負責人做的決定

以下每一項都有合理的替代方案。代理把選項攤開；負責人做選擇。

- **不用 PyTorch**，所以沒有版面模型、沒有 OCR——App 小得多、在任何 Mac 上都能跑，代價是掃描文件
  （[第 1 章](01-problem-and-scope.zh-TW.md)）。
- **Mac App 支援 PDF**，做成第二個發行設定檔，而不是讓 App 只處理文字檔。
- **一次修好三個 CI 失敗**，在第一個 PR 裡全部處理，而不是只修開 PR 時要修的那一個。
- **放棄 Python 3.10。** 處理這件事的 PR 後來關閉了，因為它的變更已經隨另一個 PR 進了 `main`。
- **暫不申請 Apple Developer 帳號**（每年 USD 99）：改用虛擬機驗證，並明白說出 App 沒有簽章。
- **把 repo 公開**，維持現有授權，作為免費工具，在先研究過已有哪些類似工具之後——
  並親自按下那個開關，因為公開之後無法撤回。
- **把案例研究放在這裡**，放在公開的 repo 裡，而不是另開一個展示用的 repo。
- **修正「MiB」的寫法**：聽完為什麼這樣寫之後，選擇補上大家熟悉的 MB，而不是只保留比較精確但比較陌生的單位。

## 找出缺陷的那些問題

負責人的問題，往往就是揭露問題的關鍵——不是因為這些問題很技術，而是因為它們問的是使用者會看到什麼。

| 問題或行動 | 找到了什麼 |
| --- | --- |
| 在負責人的 Mac 上建置 App | 21 份授權聲明被默默漏掉（[第 3 章第 7 項](03-silent-failures.zh-TW.md#7-被默默漏掉的授權聲明)） |
| 檢查負責人轉換過的一個檔案 | `&` 變成了 `&amp;`——Markdown 輸出把 HTML 實體重複跳脫了 |
| README 列出的輸出格式，網頁上卻沒有？ | `.json` 和 `.txt` 只有命令列才有 |
| 可以再確認一次授權嗎？ | 法律文件描述的是一個不支援 PDF 的專案（[第 8 項](03-silent-failures.zh-TW.md#8-描述錯了產品的法律文件)） |
| 用戶上傳沒有文字的圖片，會得到什麼？ | 一次成功的下載，內容是空檔案（[第 9 項](03-silent-failures.zh-TW.md#9-空的轉換結果被當成成功回傳)） |
| 如果上傳了不支援的格式呢？ | 中文頁面上的英文錯誤訊息，而且什麼都沒說明 |
| 為什麼是「MiB」而不是「MB」？ | 頁面除以 1,048,576，卻把結果標成 MB（[第 10 項](03-silent-failures.zh-TW.md#10-同一個檔案兩種大小)） |

這些都不需要負責人懂程式怎麼運作，每一個需要的都是有人從產品外面看它。

## 代理自己犯的錯

這些是代理的錯，而且每一個都在出貨前被抓到——有些是代理自己抓到的，更多是負責人抓到的，
全都是靠拿真實的東西來對照。

| 錯誤 | 怎麼抓到的 |
| --- | --- |
| 給負責人的建置路徑，資料夾名稱少了 `-pdf-` | 負責人的終端機：找不到這個目錄 |
| 建議用「右鍵 › 打開」繞過 Gatekeeper——Apple 在 macOS 15 已移除這個方式 | 準備虛擬機程序時，查證了 Gatekeeper 目前的行為 |
| 提議用 `--skip-editable` 修好依賴稽核，卻沒實測；專案並不是以 editable 方式安裝，所以它根本不會有作用 | 在寫修正之前，先重現 CI 的環境 |
| 加入 `pdf` 設定檔，卻沒更新法律文件 | 負責人要求再確認一次授權 |
| 找到 FreeType 的聲明要求，卻漏了 IJG 的 | 把每一份隨附的授權檔完整讀完 |
| 說某個下載檔命名行為不是刻意的；其實測試名稱就表明那是一個安全上的選擇 | 在修改之前先讀了那個測試 |
| 把一個無關的變更放進了一個 commit，而 commit 訊息沒有描述它 | 檢查 commit 時發現，拆成了兩個 |
| 在這份案例研究裡寫測試「0 個跳過」 | 讀 CI 的紀錄（[第 4 章](04-verification-strategy.zh-TW.md#打包後-app-的測試不在-ci-裡跑)） |

模式和第 3 章一樣：憑記憶、或憑單一環境就下的斷言，而不是拿東西本身來對照。

## 是什麼讓錯誤沒有出貨

- **每個變更都經過 PR**，一個 PR 只處理一件事，合併前 CI 必須全綠。代理只在負責人說要合併時才合併。
- **每個修正都附帶一個「沒有這個修正就會失敗」的測試**
  （[第 4 章](04-verification-strategy.zh-TW.md#每個回歸測試都對照-bug-驗過)）。
- **真實硬體、真實文件。** 負責人的 Mac 建置和負責人自己的檔案，找到了代理環境裡再多測試都找不到的問題。
- **個人資料不進 repo。** 負責人的真實文件只用來檢查輸出，從不提交；每個提交進來的範例都是合成的。
- **無法撤回的步驟留給負責人**——公開 repo、購買憑證、決定合併。
- **「沒驗證」是一個正當的答案。** 代理的環境連不到某些主機，也沒有 Mac。沒查核過的地方，文件就直說沒查，而不是暗示查過了。

## 給類似專案的啟示

一個代理可以撰寫並測試這種規模的產品。它無法提供的，是外部的視角：一個真的在用這個東西的人，
在自己的機器上、用自己的文件，並問它應該要做什麼。第 3 章的十個缺陷，大多數就是在這個交界處找到的。
